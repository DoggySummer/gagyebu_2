# 가계부 + 감사일기 — 1차(MVP) 설계

작성일: 2026-08-03

## 1. 개요

하루를 하나의 기록 단위로 삼아, 그날의 **감정·감사·자유 기록**과 **변동지출 내역**을 한 화면에서 함께 남기는 개인용 웹 앱. 모바일 사용을 우선한다.

기존 가계부 앱과 다른 점은 지출과 일기가 분리된 두 기능이 아니라, **하나의 "하루"라는 엔트리에 함께 담긴다**는 것이다. 캘린더에서 한 달을 펼치면 소비 패턴과 그날의 기록에 동시에 접근할 수 있다.

### 1차 범위

- 하루 기록: 기분 점수, 감사한 일, 오늘의 기록(마크다운), 즐겨찾기
- 변동지출 입력 및 조회
- 월간 캘린더(지출 히트맵)
- 즐겨찾기 목록
- 기본 통계 2종
- 카카오 소셜 로그인

### 1차 범위 밖 (2차 이후 별도 설계)

| 항목 | 사유 |
|---|---|
| AI 통계 피드백 | LLM 연동이라는 독립적인 백엔드 작업 |
| 여행 기록 | 여러 날을 묶는 별도 데이터 구조가 필요 |
| 월별 미디어 로그(책·영화·음악) | 제목·별점 기반의 다른 형태의 기록 |
| 고정지출 / 저축·투자 입력 | 매일이 아닌 월 단위 관리 성격. 별도 탭에서 입력받을 예정 |
| 고정/변동/저축 비율 통계 | 위 항목이 없으면 산출 불가 |
| 사진 첨부 | 스토리지 설계가 별도로 필요 |
| 데스크톱 전용 전체 내역 화면 | 모바일 우선 검증 후 판단 |

## 2. 사용자와 핵심 흐름

사용자는 본인 한 명이지만, 인증은 정식 회원가입 구조(카카오 소셜 로그인)로 구현한다.

**가장 잦은 흐름 — 지출 기록 (하루 여러 번)**
앱 실행 → 오늘 탭 → `가계부` 서브탭 → ＋ 버튼 → 숫자 키패드로 금액 입력 → 카테고리 칩 선택 → 메모 입력 → 완료

**하루 마무리 흐름 (하루 한 번)**
오늘 탭 → `기록` 서브탭 → 기분 점수 선택 → 감사한 일 한 줄 → 오늘의 기록 작성 → 저장

**회고 흐름**
캘린더 탭 → 히트맵에서 색이 진한 날 발견 → 날짜 탭 → 그날의 지출과 기록 확인

## 3. 데이터 모델

날짜는 모두 `Asia/Seoul` 기준으로 해석한다. `entry_date`는 시각 정보 없는 날짜(`date`)다.

### `daily_entries`

하루의 일기 부분. 사용자가 처음 저장할 때 생성(upsert)된다.

| 컬럼 | 타입 | 제약 |
|---|---|---|
| `id` | uuid | PK |
| `user_id` | uuid | Supabase `auth.users` 참조, NOT NULL |
| `entry_date` | date | NOT NULL, `(user_id, entry_date)` 유니크 |
| `mood_score` | smallint | NULL 허용, 1~5 |
| `gratitude` | text | NULL 허용, 최대 200자 |
| `note_markdown` | text | NULL 허용, 최대 10,000자 |
| `is_favorite` | boolean | NOT NULL, 기본 false |
| `created_at` / `updated_at` | timestamptz | NOT NULL |

### `expenses`

지출 1건 = 1행.

| 컬럼 | 타입 | 제약 |
|---|---|---|
| `id` | uuid | PK |
| `user_id` | uuid | NOT NULL |
| `entry_date` | date | NOT NULL |
| `amount` | integer | NOT NULL, 1 이상 100,000,000 이하 (단위: 원) |
| `category` | text | NOT NULL, 아래 6종 중 하나 |
| `memo` | text | NOT NULL, 1~100자 |
| `payment_method` | text | NULL 허용, `card` / `cash` / `transfer` |
| `created_at` / `updated_at` | timestamptz | NOT NULL |

인덱스: `(user_id, entry_date)`

### 설계 판단: `expenses`가 `daily_entries`를 참조하지 않는 이유

`expenses`는 `daily_entries.id` 대신 `user_id + entry_date`를 직접 가진다.

- 일기를 쓰지 않은 날에도 지출만 기록할 수 있어야 한다. FK로 묶으면 지출 하나 넣으려고 빈 일기 행을 먼저 만들어야 한다.
- 캘린더 히트맵은 날짜별 지출 합계만 필요하다. 조인 없이 `GROUP BY entry_date`로 끝난다.

트레이드오프로 두 테이블 사이에 DB 레벨 정합성 제약이 없지만, 애초에 서로 독립적으로 존재할 수 있는 데이터이므로 문제가 되지 않는다.

### 카테고리 (1차 = 변동지출 6종)

`식비`, `외식비`, `꾸밈비`, `문화생활`, `구독료`, `건강`

앱에서 제공하는 고정 목록이며 사용자가 편집하지 않는다. 코드에서는 상수 배열과 유니온 타입으로 관리한다.

> 출처: 사용자의 기존 가계부 스프레드시트의 변동지출 분류. 같은 시트의 고정지출(주거비·교통비·통신비·공부·보장성보험)과 저축·투자(적금·ISA·미국주식·연금저축펀드·주택청약·현금성자산)는 2차에서 별도 탭으로 다룬다.

## 4. 화면 명세

하단 탭바 3개: **오늘 / 캘린더 / ···**

로그인 성공 후 진입 화면은 **오늘 탭**이다. 이 앱의 핵심 습관이 "매일 기록하기"이므로, 켜자마자 바로 쓸 수 있어야 마찰이 가장 적다.

### 4.1 로그인

"카카오로 로그인" 버튼 하나만 있는 단일 화면. 다른 로그인 수단은 제공하지 않는다.

### 4.2 오늘 (`/entries/:date`, 기본값 = 오늘 날짜)

상단에 날짜와 즐겨찾기 토글(★), 그 아래 서브탭 `기록` / `가계부`.

즐겨찾기 토글은 그 자체가 명시적인 단일 동작이므로 누르는 즉시 저장한다.

#### `기록` 서브탭

세로 순서로 배치한다.

1. **기분 점수** — 이모지 5개(😔😐🙂😊😄)를 가로로 놓고 하나 선택. 내부적으로 1~5 정수로 저장. 선택 해제 가능.
2. **감사한 일** — 한 줄 입력. 마크다운 없는 일반 텍스트.
3. **오늘의 기록** — 마크다운 텍스트 영역.

**마크다운 편집 방식**: 모바일에서 `#`, `-` 같은 기호를 직접 타이핑하는 부담을 없애기 위해 입력창 위에 툴바 버튼 4개를 둔다.

| 버튼 | 동작 |
|---|---|
| 제목 | 커서가 있는 줄 앞에 `### ` 삽입 (이미 있으면 제거) |
| 목록 | 커서가 있는 줄 앞에 `- ` 삽입 (이미 있으면 제거) |
| 인용 | 커서가 있는 줄 앞에 `> ` 삽입 (이미 있으면 제거) |
| 굵게 | 선택 영역을 `**`로 감싼다. 선택이 없으면 커서 위치에 `****`를 넣고 가운데로 커서를 옮긴다 |

어느 경우든 조작 후 입력창에 포커스를 유지해 키보드가 닫히지 않게 한다.

저장된 뒤에는 렌더링된 결과를 보여주고, 본문을 탭하면 다시 편집 모드로 전환한다. 지원 문법은 제목·목록·굵게·기울임·인용·인라인 코드로 제한하며, 렌더링 결과는 반드시 새니타이즈한다.

**저장**: 하단에 명시적인 `저장` 버튼. 변경사항이 있을 때만 활성화된다. 저장하지 않은 변경사항이 있는 상태에서 화면을 벗어나려 하면 확인 다이얼로그를 띄운다.

#### `가계부` 서브탭

그날의 지출 목록과 합계를 보여준다. 각 항목은 `메모 · 카테고리 태그 · 금액` 한 줄로 표시한다.

**항목 추가** — 우하단 ＋ 버튼을 누르면 하단 시트가 올라온다. 시트 구성은 위에서부터 큰 금액 표시 → 카테고리 칩 6개 → 메모 입력 → 숫자 키패드. 시트가 열리면 금액 입력에 포커스가 있어 바로 숫자를 누를 수 있다. `완료`를 누르면 서버에 저장되고 시트가 닫히며, 목록 화면을 벗어나지 않으므로 여러 건을 연속으로 넣기 좋다.

결제수단은 선택 항목이므로 시트에서 접힌 상태로 두고, 필요할 때만 펼쳐서 고른다.

**항목 수정** — 항목을 탭하면 같은 시트가 기존 값이 채워진 채로 열린다.
**항목 삭제** — 항목을 좌로 스와이프하면 삭제 버튼이 노출되고, 누르면 확인 후 삭제한다.

**빈 상태** — "아직 기록한 지출이 없어요. ＋ 를 눌러 추가해보세요."

### 4.3 캘린더 (`/calendar/:year/:month`)

월 단위 그리드. 각 날짜 칸의 **배경색 진하기로 그날의 변동지출 규모**를 표현한다(히트맵). 즐겨찾기한 날에는 칸 우상단에 ★를 표시한다.

**히트맵 4단계 기준**: 표시 중인 달의 일별 지출 합계 최댓값을 기준으로 한다.

| 단계 | 조건 |
|---|---|
| 없음 | 지출 0원 |
| 1단계 | 최댓값의 33% 이하 |
| 2단계 | 최댓값의 33% 초과 66% 이하 |
| 3단계 | 최댓값의 66% 초과 |

달마다 기준이 다시 계산되므로 "이번 달 안에서 상대적으로 많이 쓴 날"을 보여준다. 절대 금액 구간을 쓰지 않는 이유는, 소비 규모가 달라져도 항상 의미 있는 대비가 유지되기 때문이다.

**저축·투자와 고정지출은 히트맵 계산에 포함하지 않는다.** 적금 30만 원을 넣은 날이 커피 4,500원 쓴 날보다 진하게 보이면 "돈을 많이 쓴 날"이라는 신호가 왜곡된다. 1차에서는 변동지출만 저장하므로 자연히 충족되지만, 2차에서 고정지출·저축이 추가되어도 이 규칙을 유지한다.

**월 이동**: 좌우 스와이프와 상단 화살표 버튼을 모두 지원한다.
**날짜 탭**: 해당 날짜의 오늘 화면으로 이동한다.
**미래 날짜**: 비활성 처리하여 선택할 수 없다.

### 4.4 ··· (더보기)

`즐겨찾기`, `통계`, `설정` 세 항목으로 이동하는 목록 화면.

즐겨찾기를 하단 탭에서 이곳으로 옮긴 이유는 자주 여는 화면이 아니기 때문이다. 하단 탭은 매일 쓰는 오늘·캘린더 두 개에 집중시킨다.

#### 즐겨찾기 (`/favorites`)

즐겨찾기한 날을 최신순 카드 리스트로 보여준다. 카드에는 **날짜 · 기분 이모지 · 감사한 일 미리보기 한 줄**이 들어간다. 목록 전체가 이미 즐겨찾기이므로 ★ 아이콘은 표시하지 않는다.

감사한 일이 비어 있으면 `note_markdown`의 첫 줄을 대신 보여주고, 그것도 없으면 미리보기를 생략한다.

카드를 탭하면 해당 날짜의 오늘 화면으로 이동한다. 20건 단위로 커서 기반 무한 스크롤.

**빈 상태** — "특별한 날을 ★로 표시해두면 여기 모여요."

#### 통계 (`/stats`)

ECharts로 두 개를 표시한다.

1. **카테고리별 지출 비율** (파이 차트) — 선택한 달의 변동지출을 6개 카테고리로 나눈다. 상단에서 월을 바꿀 수 있다.
2. **월별 지출 추이** (막대 차트) — 최근 6개월의 변동지출 총액.

데이터가 없는 달은 "이 달에는 기록된 지출이 없어요"로 대체한다.

#### 설정 (`/settings`)

로그아웃. 그 외 항목은 1차에 없다.

## 5. 디자인 시스템

방향은 **종이 다이어리 감성의 미니멀** — 따뜻한 아이보리 배경, 얇은 헤어라인 보더, 넉넉한 여백, 카테고리별 파스텔 태그. **라이트 모드 전용**이며 다크 모드는 지원하지 않는다.

## 6. 기술 아키텍처

버전과 선정 이유는 [README.md](../../../README.md) 참조.

```
[브라우저]
   │  supabase-js — 카카오 OAuth → JWT
   │
[Vercel] ── 프론트(React/Vite) + Hono API (동일 오리진)
   │  postgres.js + Drizzle (Supavisor 풀러 경유)
   │
[Supabase] ── PostgreSQL + Auth
```

프론트와 API를 Vercel 한 프로젝트에서 동일 오리진으로 서빙하므로 CORS 설정이 필요 없고, 배포 대상이 하나다.

### 인증

1. 프론트가 `supabase-js`로 카카오 로그인 → JWT 획득
2. API 호출 시 `Authorization: Bearer <JWT>` 헤더로 전달
3. Hono 미들웨어가 Supabase JWT 시크릿으로 검증하고 `user_id`를 컨텍스트에 주입
4. 검증 실패 시 401

방어를 이중으로 두기 위해, 모든 쿼리에 `user_id` 조건을 필수로 걸고 **동시에** 두 테이블에 RLS를 활성화한다.

### 계층 구조

라우트(Hono 핸들러) → 서비스 → Drizzle 쿼리로 분리한다. Drizzle 스키마 타입과 API 응답 타입은 반드시 분리한다.

도메인 기준 패키징을 따른다.

```
backend/nodejs/src/
  db/schema/{entries,expenses}.ts
  domains/
    entry/     { route.ts, service.ts, repository.ts, dto.ts }
    expense/   { ... }
    calendar/  { ... }
    stats/     { ... }
  middleware/auth.ts
```

프론트도 같은 방식으로 도메인별 폴더를 두고, 화면 단위 컴포넌트는 각 도메인 아래에 배치한다. 공용 UI 요소(칩, 시트, 태그 등)만 `components/ui`에 모은다.

### API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/entries/:date` | 일기 + 그날 지출 목록 |
| PUT | `/api/entries/:date` | 일기 부분 저장 (upsert) |
| PATCH | `/api/entries/:date/favorite` | 즐겨찾기 토글 |
| POST | `/api/entries/:date/expenses` | 지출 추가 |
| PATCH | `/api/expenses/:id` | 지출 수정 |
| DELETE | `/api/expenses/:id` | 지출 삭제 |
| GET | `/api/calendar?year=&month=` | 날짜별 지출 합계 + 즐겨찾기 여부 |
| GET | `/api/favorites?cursor=` | 즐겨찾기 목록 (20건 단위) |
| GET | `/api/stats/categories?year=&month=` | 카테고리별 합계 |
| GET | `/api/stats/monthly?months=6` | 월별 합계 |

요청 본문 검증은 서버에서 반드시 수행한다. 프론트 검증은 사용자 편의용일 뿐 신뢰하지 않는다.

## 7. 에러 처리와 엣지 케이스

| 상황 | 처리 |
|---|---|
| 저장 요청 실패 | 토스트로 알리고 **입력 내용을 화면에 유지**한다. 사용자가 쓴 글을 절대 잃지 않는 것이 최우선 |
| 조회 요청 실패 | 해당 영역에 재시도 버튼이 있는 오류 상태 표시 |
| JWT 만료 | 자동 갱신 시도, 실패 시 로그인 화면으로 이동 |
| 서버리스 콜드 스타트 | 첫 요청 지연을 스켈레톤 UI로 가림 |
| Supabase 무료 티어 일시정지 | 서비스 불가 안내 화면 (7일 무요청 시 발생) |
| 미래 날짜 | 캘린더에서 선택 불가 |
| 같은 날 중복 저장 | `(user_id, entry_date)` 유니크 제약 + upsert로 처리 |
| 금액 0 또는 음수 | 서버에서 거부, 시트의 완료 버튼도 비활성 |
| 필수값 누락 (금액·카테고리·메모) | 완료 버튼 비활성 |
| 자정 넘김 | 화면에 보이는 날짜를 기준으로 저장. 앱이 열린 채 날짜가 바뀌어도 사용자가 보고 있던 날짜에 기록된다 |

지출 추가는 낙관적 업데이트를 적용해 즉시 목록에 반영하고, 실패하면 되돌리며 토스트로 알린다. 일기 저장은 명시적 버튼이므로 낙관적 업데이트를 쓰지 않는다.

## 8. 테스트 전략

| 대상 | 도구 | 범위 |
|---|---|---|
| 서비스 로직 | Vitest | 히트맵 단계 계산, 통계 집계, 검증 규칙 |
| DB 통합 | Vitest + Supabase CLI 로컬 스택 | upsert 동작, 유니크 제약, user_id 격리 |
| 컴포넌트 | Vitest + RTL | 마크다운 툴바 삽입, 시트 입력 검증, 저장 버튼 활성화 조건 |
| E2E | Playwright (모바일 뷰포트) | 지출 추가 → 캘린더 반영, 일기 저장 → 재진입 시 유지, 즐겨찾기 토글 → 목록 반영 |

특히 **다른 사용자의 데이터가 조회되지 않는지**는 통합 테스트에서 반드시 검증한다.
